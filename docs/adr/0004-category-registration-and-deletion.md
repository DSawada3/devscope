# 0004: 作業カテゴリの登録と各登録一覧からの削除

- 日付: 2026-10-25
- 状態: 採用

## 背景・受入条件

作業カテゴリも利用者が登録し、タスク・開発工程・プロジェクト・作業カテゴリの各登録画面で一覧と削除操作を提供する。
受入条件は、追加カテゴリの保存・タスク選択・カレンダー表示と絞り込み、各一覧の削除と再起動後の維持、既存記録の保全、使用中の削除拒否、失敗時の一覧と入力保持、空一覧からの復帰とする。

## 選択肢

- 固定カテゴリを維持する：既存コードの変更は少ないが、利用者の作業分類を登録できない。
- 削除を履歴へ連鎖反映する：参照整合性は保てるが、過去の予定・実績を意図せず失う。
- 削除済みフラグで候補から隠す：履歴を保持できるが、復元・再登録・表示対象の仕様が必要になる。
- カテゴリを登録データにし、使用中の分類は削除を拒否する：履歴と参照整合性を維持しつつ、未使用項目を削除できる。

## 決定と理由

カテゴリの正本を Zustand の `categories` と Rust JSON へ移す。カテゴリは `{ id, label, color, background }` を持つ。旧4カテゴリの ID・名称・色は維持し、旧 JSON でカテゴリ項目が省略された場合のみ初期定義を補う。明示的な空配列を初期値で置換しない。新しい ID は `category-N` で採番し、削除後も再利用しない。名前は trim 後1〜60 UTF-16コード単位で一意とする。追加カテゴリは既存の緑色を使用し、色編集は今回の範囲に含めない。

フロントエンドは固定の Category 列挙型を文字列 ID へ変更する。Rust は入力の構文だけでなく、保存データのカテゴリ定義に存在する ID かを検証する。フィルター、タスク、作業ブロックの追加・更新と保存ファイル全体を対象とする。保存された名称・色と参照の不整合は破損として拒否する。既存の「開発時間」は引き続き旧 `development` の集計とし、追加カテゴリの時間は合計時間・件数に含める。

タスクは ID で削除し、作業内容をコピー済みの予定・実績は変更しない。開発工程・プロジェクトは名前、カテゴリは ID で削除する。タスクまたは予定・実績に使用されている場合は `IN_USE` と理由を返し、削除しない。工程・プロジェクトの使用判定では旧履歴の前後空白を除去して比較する。これにより、履歴由来の候補が削除後に再出現する問題も避ける。

削除 API は既存 BlockStore のロック・保存方式を使い、保存成功後にストアと画面へ反映する。使用中・保存失敗・存在しない対象は一覧を維持する。登録途中のフォームで選択中の未使用候補を削除した場合、工程・プロジェクトは未指定へ戻し、カテゴリは残る先頭候補へ切り替える。カテゴリが0件の場合は登録を促す。

ブラウザー版もメモリ内で使用判定と削除を行う。再読み込みでデモへ戻る従来の動作は維持する。新規依存・追加権限はない。

## 互換性・検証

既存 JSON version 1 に `categories` / `nextCategoryId` を追加する。旧 JSON の省略項目は初期4件と1で補う。古いアプリへのダウングレードはカスタムカテゴリ・追加項目に非対応。
Rust テストでカテゴリの追加・参照検証・絞り込み・削除・旧ファイル互換・空配列・使用中拒否・保存失敗時のファイル保全を検証する。Chrome テストで各一覧の登録と削除、保存失敗と再試行、入力と記録の維持、追加カテゴリの表示・絞り込みと復元を検証する。実機の WebView2 / IPC は別途確認する。
